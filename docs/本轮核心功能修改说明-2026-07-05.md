# 本轮核心功能修改说明

时间：2026-07-05
作者：Jan
背景：三天后线下黑客松要用这套系统做现场管理，本轮目标不是追求花哨效果，而是优先排掉核心链路里会影响现场结果准确性的风险。

## 1. 本轮改动目标

这次主要围绕五条核心链路做加固：

1. 选手端：作品提交、撤回、截图上传必须只允许本队队长操作。
2. 观众端：观众只能给已经发布到作品展厅的作品投票，公开接口不能泄露投票人明细。
3. 评委端：评委只能给已发布作品评分，草稿和正式提交的范围要一致。
4. 管理端：最终排行榜发布必须基于完整投票、完整评分和锁分状态，不能提前发布不完整结果。
5. 大屏端：大屏只展示后端真实状态，不能通过本地按钮制造“假同步”。

术语说明：

- API：Application Programming Interface，应用程序接口。这里指前端调用后端的 HTTP 地址，例如 `/api/work/submit`。
- strict 鉴权：后端强制检查登录 session 和用户角色。前端隐藏按钮只是体验层，真正的安全边界必须在后端。
- published：作品状态为已发布。只有 published 作品才进入作品展厅、观众投票和评委评分范围。
- snapshot：最终发布时生成的一份固定结果快照。发布后排行榜读取快照，不再跟随实时票数变化。
- MIME：文件类型声明，例如 `image/png`。它是浏览器或请求声明的类型，不等于文件真实内容。
- 前端本地状态：只存在浏览器内存里的临时变量。它能改变当前页面显示，但不会写入后端，也不会同步到其他端。

## 2. 已修改文件与作用

### 2.1 `server/index.js`

这是后端 HTTP 入口，负责接收前端请求、校验权限、调用数据仓库。

本轮改动：

- 新增 `enforceTeamLeaderWork()`：选手作品提交、撤回、上传截图前，后端确认当前用户必须是本队队长。
- 新增 `enforcePublishedVoteTarget()`：观众投票前，后端确认目标队伍存在已发布作品。
- 新增 `redactVoteResultsForPublic()`：公开投票结果接口只返回票数和投票人数，不返回 `voters` 明细。
- 评委草稿接口也按已发布作品过滤，避免未发布队伍进入评分数据。
- 新增 `isSupportedImagePayload()`：上传图片除了看 `image/png` 等声明，还会检查 PNG/JPG/GIF/WEBP 的真实文件头。

影响：

- 普通队员不能再绕过前端按钮提交或撤回作品。
- 观众不能给未发布作品投票。
- 公开页面拿不到“谁投给谁”的明细。
- 伪装成图片的非图片内容会被拒绝上传。

### 2.2 `server/worksRepository.js`

这是本地 JSON 模式下的作品数据仓库。开发环境、兜底环境会用它读写 `data/works.json`。

本轮改动：

- `submitWork()` 在重新提交作品时，强制清空 `reviewedAt`、`reviewedBy`、`reviewNote`。

为什么要改：

- 如果一个作品先被管理员退回，再由选手重新提交，新版本应该重新进入待审核状态。
- 旧审核人、旧审核时间、旧退回备注不能继续挂在新提交上。
- MySQL 仓库原本已经在 SQL 层清空这些字段，这次是把 JSON 仓库行为补齐。

### 2.3 `server/resultSnapshotService.js`

这是最终排行榜快照的计算和发布前校验逻辑。

本轮改动：

- 最终发布前要求所有已发布作品都必须存在投票结果行。
- 最终快照里的评委评分来源只保留最终参赛队伍，避免隐藏队伍评分记录混进去。

影响：

- 管理员不能在投票数据缺行时误发布排行榜。
- 最终结果的来源数据范围更干净，便于事后追溯。

### 2.4 `admin.html`

这是管理端页面结构。

本轮改动：

- 最终发布流程提示从“关闭投票后发布”调整为“关闭投票 + 锁定全部评分 + 发布快照”。

影响：

- 管理员看到的操作步骤和后端真实规则一致，减少现场误操作。

### 2.5 `src/admin.js`

这是管理端主要交互脚本。

本轮改动：

- 发布最终排行榜按钮的可用条件改为：投票已关闭、专家评分已锁定、尚未发布最终快照。
- 管理端状态文案同步展示评分锁定要求。

影响：

- 页面不会误导管理员提前发布结果。

### 2.6 `src/site.js`

这是用户端页面主要交互脚本，覆盖选手、评委、观众视图。

本轮改动：

- 排行榜缺省提示改为：需要关闭投票并锁定专家评分后，才能发布最终排行。

影响：

- 前台看到的状态说明和管理端、后端规则保持一致。

### 2.7 `tests/server.test.js`

这是后端接口测试。

本轮新增或强化的关键测试：

- 普通队员不能调用作品提交、撤回、上传截图接口。
- 观众不能给未发布作品投票。
- 公开投票结果接口不能返回 `voters` 明细。
- 评委评分草稿和正式提交都只作用于已发布作品。
- 最终发布必须包含所有已发布作品的投票结果。
- 图片上传必须检查真实图片文件头。
- 退回作品重新提交时必须清空旧审核信息。

### 2.8 `tests/logic.test.js`

这是前端逻辑和静态规则测试。

本轮改动：

- 增加管理端最终发布文案、按钮条件、前台提示的防回归检查。
- 增加大屏首次读取后端阶段时必须应用当前阶段的防回归检查。
- 增加大屏组队页不保留本地抢位按钮、投票页轮询、最终结果页必须等待后端快照的检查。

### 2.9 `src/app.js`

这是大屏端主交互脚本，负责读取后端阶段、团队、投票、最终结果等状态并渲染大屏。

本轮改动：

- 移除大屏组队页里的 `抢队长位`、`认领职责`、`抢占赛道` 本地按钮。
- 组队大屏改成只读展示：已有人占位时显示 `后端同步`，无人时显示 `待认领`。
- 投票进度、投票结果、最终结果三个视图打开时，每 5 秒重新拉取一次投票数据。
- 最终结果页不再用实时票数临时计算冠军；只有 `/api/results/latest` 返回已发布快照时才展示冠军。
- 初始化大屏时会同步读取最新结果快照，避免页面刚打开时使用旧的本地推导结果。

为什么要改：

- 之前大屏组队页按钮只改浏览器本地变量，不会调用 `/api/team/*` 后端接口，所以选手端真实加入队伍后，大屏可能看起来“不一致”。
- 大屏是现场展示端，原则上应该只呈现后端真实状态，不应该承担写入业务数据的职责。
- 最终冠军属于现场关键结果，必须由管理端发布快照后固定下来，不能由大屏自己根据临时票数提前推导。

### 2.10 `src/logic.js`

这是前端共享逻辑函数文件。

本轮改动：

- `shouldApplyAdminStageChange()` 现在允许第一次读取到后端阶段时立即应用。

为什么要改：

- 之前逻辑要求已经存在旧同步 key 才切换阶段，导致裸打开 `/index.html` 时，如果后端当前阶段已经是结果页，大屏可能仍停在默认首页。

### 2.11 `styles.css`

这是大屏和官网的主要样式文件。

本轮改动：

- 新增 `team-role-status`、`team-action-status` 只读状态样式。
- 保留原有赛博风格视觉，但禁用指针交互，避免现场误以为大屏按钮可以真实写入后端。

### 2.12 `tests/server.test.js`

本轮补充：

- 最终结果发布成功类测试显式传入静态评委用户列表。

为什么要改：

- 后端发布最终结果时会检查“所有活跃评委是否都锁分”。测试如果不固定评委名单，就可能读到本地真实用户库里的更多评委，导致测试不是在验证发布逻辑，而是在被外部数据污染。

## 3. 对三类用户的结果

### 3.1 选手端

现在的规则是：队长能提交、撤回、上传作品截图；普通队员不能绕接口做这些操作。

作品截图保存路径是 `assets/uploads/works/<teamId>/`。这里仍然需要上线前确认服务器部署不会清空上传目录。

### 3.2 评委端

评委评分范围现在以已发布作品为准。也就是说，管理员没有发布到作品展厅的作品，不应该出现在评委评分范围里。

正式提交通常按五个维度计算总分：

1. 创新性
2. 技术实现
3. 业务价值
4. 可行性
5. 演示表现

每个评委对每个作品提交一组分数，后台再统计平均分。最终结果发布前，需要管理员确认所有评委都提交，并锁定评分。

### 3.3 观众端

观众只能在投票窗口开启时，从作品展厅给已发布作品投一票。公开投票结果不会再暴露用户 ID 到队伍 ID 的投票映射。

### 3.4 大屏端

大屏端现在是后端真实状态的展示层：

- 组队结果来自 `/api/teams`。
- 投票结果来自 `/api/vote-results`。
- 最终冠军来自 `/api/results/latest` 的发布快照。
- 阶段切换来自 `/api/admin/state`。

如果现场发现大屏没变，排查顺序应该是：先看后端接口数据是否变化，再看大屏是否轮询成功，最后再看样式或渲染问题。

## 5. 仍需上线前人工确认

1. 生产环境开启 `AUTH_ENFORCEMENT=strict`。
2. `assets/uploads/works/` 上传目录必须持久化，不能被部署覆盖。
3. 用户上传截图但不提交作品时，目前文件会留在上传目录；后续可以加临时目录或定时清理。
4. 飞书文档链接能不能打开，取决于飞书文档本身的共享权限；系统只能保存 URL，不能替文档自动授权。
5. 本轮是本地代码修改和测试，是否同步到服务器，仍取决于后续部署流程。
