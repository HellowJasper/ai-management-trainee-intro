# 核心功能对抗式排雷报告

时间：2026-07-05
目标：线下黑客松上线前排查选手端、评委端、观众端和管理端的核心风险，优先保证“不出错”。

## 1. 审查方式

本轮采用 subagent 并行审查。

- 选手端 subagent：重点看作品提交、作品截图、飞书文档链接、队伍成员权限。
- 评委端 subagent：重点看评分草稿、正式提交、锁分、最终结果快照。
- 观众端 subagent：重点看作品展厅可见性、一人一票、投票窗口、公开投票数据。
- 主线程 Jan：汇总发现，补测试，修 P0/P1 风险，补管理端文档。

术语说明：

- 对抗式审查：不是按正常用户路径点击，而是故意从接口、边界状态、未发布数据、权限绕过角度找漏洞。
- strict 鉴权：后端强制根据登录 session 判断用户身份和权限。代码里对应 `AUTH_ENFORCEMENT=strict`。
- published：作品已由管理员发布，普通观众和评委才应该看到。
- voters：投票仓库里保存的“谁投给了谁”的映射，属于敏感数据。
- snapshot：最终发布时固化的结果快照，发布后前台排行榜读取它，而不是继续读实时票数。

## 2. 已修复的核心风险

### 2.1 非队长绕过前端提交作品

风险：前端只让队长编辑，但服务端以前只校验“是否本队成员”。普通队员可以绕过按钮，直接调用接口提交、撤回或上传作品截图。

修复：

- `server/index.js` 新增 `enforceTeamLeaderWork()`。
- `/api/work/submit`、`/api/work/withdraw`、`/api/work-assets` 都改为服务端校验当前用户必须是本队队长。
- 新增测试：`strict work APIs require the current team leader`。

### 2.2 观众给未发布作品投票

风险：作品展厅只展示已发布作品，但投票接口以前只看 `vote-results` 里有没有 teamId。懂接口的人可以给未发布队伍投票，导致前台看不到、后台有票数。

修复：

- `server/index.js` 新增 `enforcePublishedVoteTarget()`。
- `/api/vote/cast` 投票前必须确认目标队伍有 `published` 作品。
- 新增测试：`vote API rejects unpublished work targets for audience votes`。

### 2.3 公开投票结果暴露 voters

风险：`/api/vote-results` 是公开接口，以前会返回 `voters`，也就是用户 ID 到队伍 ID 的投票映射。

修复：

- `server/index.js` 新增 `redactVoteResultsForPublic()`。
- 公开接口只返回票数和 `votersCount`，不返回 `voters` 明细。
- 新增测试：`API lists vote results with the confirmed ranking point scale` 中断言 `voters` 被脱敏。

### 2.4 最终发布可能漏掉已发布作品

风险：如果某个已发布作品没有出现在投票结果里，旧逻辑会静默漏掉它，仍然允许发布最终结果。

修复：

- `server/resultSnapshotService.js` 的 `assertFinalResultPublishable()` 现在要求所有已发布作品都必须有投票结果行。
- 最终结果快照的 `source.judge.records` 只保留最终结果涉及的队伍，避免带出隐藏队伍评分记录。
- 新增测试：`admin result publish API rejects when a published work is missing from vote results`。

### 2.5 评委暂存可写入未发布队伍

风险：正式提交评分已经会按已发布作品过滤，但暂存评分以前没有过滤，可能污染后台进度数据。

修复：

- `/api/judge/scores` 草稿保存前也调用 `scopeJudgeScorePayloadToTeams()`。
- 新增测试：`judge draft API scopes scores to published works`。

### 2.6 管理端最终发布文案与后端规则不一致

风险：页面以前提示“关闭投票后即可发布”，但后端真实规则是“关闭投票 + 锁定专家评分”。

修复：

- `admin.html` 将流程 02 改为“必须：锁定全部评分”。
- `src/admin.js` 将发布按钮条件改为 `voteReady && scoreReady && !publishAlreadyComplete`。
- `src/site.js` 管理员看到的排行榜缺省提示同步为“需要关闭投票并锁定专家评分后，才能发布最终排行”。
- `tests/logic.test.js` 补充防回归断言。

### 2.7 图片上传只相信前端声明的 MIME

风险：接口以前只检查 `data:image/png` 这类声明和大小，没有检查真实文件头。攻击者可以把普通文本或其他内容伪装成图片上传，导致作品展厅图片异常，甚至给后续静态资源处理留下隐患。

修复：

- `server/index.js` 新增 `isSupportedImagePayload()`。
- 作品截图和后台星锐图片上传都会校验 PNG、JPG、GIF、WEBP 的真实文件头。
- 新增测试：`work screenshot upload rejects image data that does not match the declared type`。

### 2.8 退回作品重新提交可能残留旧审核信息

风险：本地 JSON 数据仓库里，选手重新提交退回作品时，如果请求体带着旧 `reviewedAt`、`reviewedBy`、`reviewNote`，旧审核痕迹会进入新的待审核版本。MySQL 版本已在 SQL 层清空，但本地开发和 JSON 兜底路径不一致。

修复：

- `server/worksRepository.js` 在 `submitWork()` 中强制清空审核人、审核时间和审核备注。
- 与 `server/mysqlWorksRepository.js` 的 `ON DUPLICATE KEY UPDATE reviewed_by='', reviewed_at=NULL, review_note=''` 行为保持一致。
- 新增测试：`resubmitting rejected work clears stale review metadata`。

## 3. 仍需上线前人工确认

1. 生产环境必须开启 strict 鉴权

检查项：`AUTH_ENFORCEMENT=strict`。
原因：前端隐藏按钮不是安全边界，后端 session 权限才是最终边界。

2. 上传目录必须持久化

作品截图写入 `assets/uploads/works/`。如果服务器部署会清空该目录，图片会丢。需要确认线上上传目录不会被部署覆盖。

3. 未提交上传文件缺少清理机制

用户上传截图但不提交作品时，文件会留在上传目录。建议后续加临时目录或定时清理。

4. 飞书文档权限由飞书本身决定

系统只能保存和打开 `docUrl`。飞书文档能不能被公司同事打开，取决于文档共享权限。

## 4. 最低上线口径

上线前只要以下链路跑通，就能支撑现场：

1. 选手队长提交作品，普通队员不能绕过提交。
2. 管理员审核并发布作品。
3. 观众只能给已发布作品投票。
4. 评委只能对已发布作品评分。
5. 管理员关闭投票、确认评分齐全、锁定评分。
6. 管理员发布最终快照，前台排行榜读取快照。
