## 1. 术语说明

- 严格鉴权（strict auth）：后端接口必须检查当前登录会话和权限。代码里对应 `AUTH_ENFORCEMENT=strict`。
- 默认放行（fail-open）：系统在缺配置或非严格模式下放过权限检查。它的问题是“配置漏了就变成开放系统”。
- 状态机（state machine）：业务对象只能按指定顺序改变状态。例如作品应从 `draft` 到 `submitted` 到 `published/rejected`，不能随意从 `published` 被选手撤回。
- 幂等（idempotent）：同一个操作重复执行，结果不会重复产生副作用。例如“发布最终结果”重复点击不应生成多个不同快照。
- CORS（Cross-Origin Resource Sharing，跨源资源共享）：浏览器允许一个域名访问另一个域名 API 的规则。
- SameSite：Cookie 的跨站发送策略。前后端不同域时，`SameSite=Lax` 经常会导致登录 Cookie 不随请求发送。
- 快照（snapshot）：把某一刻的最终结果固化下来，后面即使票数或评分变化，已发布结果也应以快照为准。

## 2. 关键结论

当前项目不是“完全没做权限和流程”，相反已经有不少保护：作品列表对普通用户过滤未发布作品，投票接口会检查投票窗口，MySQL 投票有事务，后台 API 在 strict 模式下有权限检查，作品展厅只展示已发布作品。

真正的问题在于：几个关键边界没有闭环。一旦部署配置漏掉、管理员误操作、选手在发布后更新作品，或者最终结果未等评分完整就发布，系统会出现“前端看起来正常、后端数据已经被改坏”的情况。

优先修复顺序建议：

1. P0 鉴权/部署默认值。
2. P0 静态数据暴露。
3. P0 最终结果发布前置条件。
4. P1 作品状态流转。
5. P1 上传文件持久化。
6. P1 会话与角色变更一致性。

## 3. P0：必须优先处理

### P0-1. Serverless 入口不会强制 strict，Vercel 环境变量漏配时会权限放开

证据：

- `api/index.js:1-5` 直接调用 `createServer()`。
- `server/index.js:1718-1727` 只有 CLI 启动时才默认设置 `AUTH_ENFORCEMENT=strict` 和 `DATA_BACKEND=mysql`。
- `server/index.js:459-462` 在非 strict 模式下，`enforcePermission` 会直接返回空会话或已有会话，不真正拦截权限。
- `server/index.js:834-841` 非 strict 模式允许前端提交任意 role 创建本地会话。

第一性原理分析：

权限系统的安全边界必须在后端强制执行，而不能依赖“部署时记得配环境变量”。Vercel 的 `api/index.js` 是函数入口，它不会执行 `require.main === module` 分支。因此一旦 Vercel Dashboard 没设置 strict，后台接口就可能从“必须管理员”变成“默认放行”。

影响：

- 未登录用户可能调用管理接口。
- 任意人可能创建 `admin` 本地会话。
- 数据后端可能回落到 JSON 文件，而不是 MySQL。

建议：

- 在 `createServer()` 或 `api/index.js` 增加生产环境启动校验：缺少 `AUTH_ENFORCEMENT=strict`、`DATA_BACKEND=mysql`、数据库配置时直接抛错。
- `isLocalRoleLoginAllowed` 默认应为 false，只允许显式 `ALLOW_LOCAL_DEV_LOGIN=true` 且 `NODE_ENV !== production`。
- 为 `/api/admin/*` 增加一条测试：未配置 strict 时生产环境必须启动失败，而不是放行。

### P0-2. `/data/*` 静态暴露可能泄露审计、评分、角色数据

证据：

- `vercel.json:67-73` 给 `/data/(.*)` 配了响应头，说明该路径在静态部署中是公开资源。
- `.gitignore:13` 只忽略 `data/sessions.json`，未忽略 `data/audit-logs.json`、`data/judge-scores.json`、`data/user-roles.json` 等敏感数据。
- 管理接口本身对审计日志有权限保护：`server/index.js:1240-1248` 使用 `canAdmin`，但静态 `/data/*` 会绕过这层 API 权限。

第一性原理分析：

敏感数据不能同时走“受权限保护的 API”和“公开静态目录”。只要静态服务器能直接访问文件，API 权限就失效。

影响：

- 评委评分、操作日志、用户角色可能被直接下载。
- 若 JSON 后端在本地或某些部署里写入 `data/`，泄露面更大。

建议：

- 删除 Vercel 对 `/data/(.*)` 的公开静态支持。
- 把所有运行时 JSON 数据迁移到非 publicRoot 目录，例如 `/var/lib/ai-intro/data`。
- `.gitignore` 中显式忽略 `data/*.json`，只保留安全的 seed/template 文件。

### P0-3. 最终结果发布不要求评委评分完整或锁定

证据：

- `server/resultSnapshotService.js:76-88` 发布前只检查投票状态为 `closed/published` 且有排名队伍。
- `src/logic.js:627-642` 没有专家评分时会把分数算作 `0`。
- `server/index.js:1267-1278` 发布结果时读取投票和评分后直接生成快照。
- `tests/server.test.js:2789-2864` 明确测试“只要求投票结束，不要求评委评分锁定”。
- `tests/server.test.js:2866-2928` 明确测试“活跃评委没有 locked 分数也允许发布”。

第一性原理分析：

最终结果是不可逆的业务承诺，发布前置条件必须覆盖所有构成最终分数的数据源。当前公式是专家评分 70% + 大众投票排名 30%，但发布条件只检查了投票，没检查专家评分完整性。缺失评分被算成 0，会直接改变排名。

影响：

- 管理员误点发布后，最终快照可能包含不完整评分。
- 某些队伍会因缺失评分被错误拉低。
- 后续补评分不会自动修正已经发布的快照。

建议：

- 发布前必须检查：所有 active judge 对所有进入最终排名的队伍均已 `locked`。
- 如果现场确实允许“不完整评分发布”，后台必须显示强确认：缺几位评委、缺哪些队伍、是否仍然发布。
- 调整现有测试，把“允许缺评分发布”改为“缺评分返回 409”。

## 4. P1：高风险流程漏洞

### P1-1. 已发布作品仍可被选手更新或撤销

证据：

- 前端把 `published` 状态显示为“提交更新”：`src/site.js:1849-1853`。
- 前端允许 `published` 状态撤销：`src/site.js:2051`、`src/site.js:3273-3276`。
- 后端提交接口未检查当前状态：`server/index.js:1163-1170`。
- MySQL 提交会把已有记录状态覆盖为 `submitted` 并清空审核字段：`server/mysqlWorksRepository.js:168-189`。
- MySQL 撤销直接把状态改回 `draft`：`server/mysqlWorksRepository.js:221-229`。
- JSON 撤销同样直接改回 `draft`：`server/worksRepository.js:144-153`。

第一性原理分析：

作品审核发布后，作品展厅和评委/公众看到的是“已审核版本”。如果选手能在发布后直接更新或撤销，管理员审核就被绕过了。

影响：

- 已发布作品可被队长撤回，作品展厅突然消失。
- 已发布作品可被替换内容，管理员审核结论失效。
- 排行榜或评分时看到的作品版本可能不一致。

建议：

- 状态机改为：`published` 后选手不能直接覆盖，只能创建 `revision/submitted` 版本，管理员审核后再替换发布版本。
- 最小修复：后端拒绝 `published` 状态下的 submit/withdraw，返回 409。
- 前端移除 published 状态下的“提交更新”和“撤销提交”。

### P1-2. 作品截图上传只检查参赛权限，不检查是否属于自己的队伍

证据：

- `/api/work-assets` 只调用 `canSubmitWork`：`server/index.js:546-550`。
- 正式提交作品会检查队伍归属：`server/index.js:1168-1169`。
- 文件保存路径由 payload 的 `teamId` 决定：`server/index.js:205-245`。

第一性原理分析：

上传接口产生的副作用是“向某个队伍目录写文件”。既然写入目标由 `teamId` 决定，就必须验证这个 `teamId` 是否是当前用户所在队伍。否则任何参赛选手都能向其他队伍目录上传图片。

影响：

- A 队选手可向 B 队作品目录写入截图。
- 即使后续提交不能引用，也会污染文件目录和审计日志。

建议：

- 在 `/api/work-assets` 上传前调用 `enforceJoinedTeamWork(session, payload.teamId)`。
- 审计日志记录实际 session user 和 teamId。

### P1-3. 投票窗口状态可以从 `published` 改回 `voting`

证据：

- JSON 版本只校验 status 值是否合法：`server/voteResultsRepository.js:17-24`。
- JSON 状态更新直接覆盖：`server/voteResultsRepository.js:158-170`。
- MySQL 版本同样只校验合法值再 upsert：`server/mysqlVoteResultsRepository.js:267-283`。

第一性原理分析：

投票状态应是单向状态机：`voting -> closed -> published`。发布结果后重新打开投票，会使已发布快照、当前票数和现场口径互相矛盾。

影响：

- 结果发布后还能重新投票。
- 最新票数和最终快照不一致，后台难以解释。

建议：

- 增加状态流转表，禁止 `published -> voting/closed`。
- 如果确实需要“回滚发布”，应做独立管理员操作，并记录强审计。

### P1-4. 上传文件存储在容器内，重部署会丢失

证据：

- 头像/星锐图片写入 `assets/uploads/trainees/...`：`server/index.js:184-201`。
- 作品截图写入 `assets/uploads/works/...`：`server/index.js:231-245`。
- `.gitignore:18` 忽略 `assets/uploads/`。
- 部署脚本删除旧容器：`deploy_to_88.sh:45-47`。
- 新容器未挂载 volume：`deploy_to_88.sh:72-80`。

第一性原理分析：

Docker 容器文件系统是临时层，容器删除后文件消失。数据库只保存路径，不能保存文件本体。

影响：

- 管理员上传成功，重部署后图片 404。
- 作品展厅/星锐档案图片丢失。

建议：

- Docker 挂载 `/app/assets/uploads` 到宿主机目录，例如 `/data/ai-intro/uploads:/app/assets/uploads`。
- 更长期方案：改用对象存储或内网文件服务。
- 增加部署前后上传文件持久化测试。

### P1-5. 用户角色修改后，旧 session 仍保留旧权限

证据：

- session 创建时把 permissions 写进 session：`server/authSessionRepository.js:72-85`、`server/mysqlAuthSessionRepository.js:77-90`。
- 读取 MySQL session 时如果已有 permissions，不会按最新角色/用户状态重新计算：`server/mysqlAuthSessionRepository.js:96-114`。
- 用户角色更新只更新 users/role_assignments：`server/mysqlUserRoleRepository.js:64-94`，没有清理该用户已有 sessions。

第一性原理分析：

权限变更必须尽快影响已登录会话。否则管理员撤销某人的 admin 角色后，该人旧 Cookie 仍能继续使用后台权限。

影响：

- 被降权或禁用的用户继续访问原权限接口。
- 现场临时改权限时结果不可控。

建议：

- 每次 `getSession` 时根据当前用户角色表重新计算权限，或者给 session 加短 TTL。
- 管理员修改用户角色后删除该 userId 的所有 session。
- API 端不要长期信任 session_json 里的 permissions。

### P1-6. Vercel 静态页面可能绕过 Node 的页面保护

证据：

- Node 静态服务里确实保护后台/大屏页：`server/index.js:1701-1708`。
- 但 Vercel 只把 `/api/(.*)` 送到函数：`vercel.json:86-88`。
- `/admin` 被改写到静态 `admin.html`：`vercel.json:76-84`。

第一性原理分析：

页面保护如果只写在 Node 的 `serveStatic` 前，而线上静态页由 Vercel 直接托管，就不会经过 Node 保护逻辑。

影响：

- 未登录用户可打开后台页面壳。
- 如果 P0-1 同时发生，接口也可能被调用。

建议：

- Vercel 使用 middleware 检查 session。
- 或让 `/admin`、`/screen`、`/index` 都经过 Node server，由 Node 统一鉴权。

## 5. P2：中风险缺口与一致性问题

### P2-1. 最终结果发布不是幂等操作，会生成多个快照

证据：

- JSON 发布把新快照插到数组最前：`server/resultSnapshotRepository.js:52-64`。
- MySQL 发布每次 insert 新行：`server/mysqlResultSnapshotsRepository.js:71-92`。
- 数据表没有唯一约束或 source hash：`db/schema.mysql.sql:162-170`。

影响：

- 重复点击或网络重试会产生多个正式快照。
- “最新快照”取决于时间和 id，审计口径变复杂。

建议：

- 为同一 source 生成 hash，重复发布返回已有快照。
- 或把发布拆成“预览快照”和“确认发布”，确认后禁止再次发布，除非走撤销/重发流程。

### P2-2. MySQL 队伍成员缺少数据库级“一个用户只能在一个队伍”唯一约束

证据：

- 表结构只有 `(team_id, user_id)` 唯一：`db/schema.mysql.sql:52-67`。
- 代码通过事务先删除该 userId 再插入新队伍：`server/mysqlTeamRepository.js:315-333`。

第一性原理分析：

应用层删除再插入可以减少重复，但并发请求下数据库才是最终一致性边界。没有 `UNIQUE KEY(user_id)`，两个并发事务可能把同一用户插入不同队伍。

建议：

- 增加 `UNIQUE KEY uq_team_member_global_user (user_id)`。
- 对顾问/虚拟占位用户另设规则，避免误伤。

### P2-3. 用户角色更新不是事务，失败后可能出现半更新

证据：

- `upsertUser` 先 upsert 用户，再 disable 旧角色，再并发插入新角色：`server/mysqlUserRoleRepository.js:64-94`。
- 这几步没有包在 transaction 里。

影响：

- 插入新角色失败时，旧角色已被禁用，用户变成无有效角色。
- 管理员端看到的状态与预期不一致。

建议：

- 使用 MySQL transaction 包住用户和角色变更。
- 写入失败时 rollback。

### P2-4. JSON 作品仓库 `submittedBy` 字段重复定义

证据：

- `server/worksRepository.js:38` 先写 `submittedBy: work.submittedBy || work.userId`。
- `server/worksRepository.js:40` 又写一次 `submittedBy: work.submittedBy`，覆盖了上一行。

影响：

- 旧数据或导入数据只有 `userId` 时，提交人会丢失。
- MySQL 版本也只读取 `submittedBy/submitted_by`：`server/mysqlWorksRepository.js:70-71`。

建议：

- 删除重复字段，保留 `submittedBy || userId` 兼容逻辑。
- 增加迁移测试：只有 `userId` 的旧作品记录仍能保留提交人。

### P2-5. 前后端分离部署的 API Base、CORS 和 Cookie 组合脆弱

证据：

- 前端服务器默认 API Base 为 `http://localhost:5173`：`server/frontendServer.js:7`。
- 前端请求带 cookie：`src/data.js:85-89`。
- Cookie 构造为 `SameSite=Lax` 且没有 `Secure`：`server/index.js:284-289`。
- CORS 预检只写 allow methods/headers：`server/index.js:521-525`，具体 origin 逻辑需依赖上方配置。

影响：

- 别的电脑访问前端时，`localhost:5173` 指向访问者自己的电脑，不是服务器。
- 前后端不同域时，登录 Cookie 可能不发送。

建议：

- 生产尽量同源反代：用户只访问 `http://192.168.1.88:8083`。
- 如果必须跨域，显式设置 `API_BASE_URL`、`CORS_ALLOW_ORIGIN`，Cookie 使用 `SameSite=None; Secure` 并配 HTTPS。

### P2-6. 飞书登录用户没有角色时会默认变成 public

证据：

- `server/index.js:775-779`：角色数为 0 时创建 `public` session。

影响：

- 未被后台授权的飞书用户可直接成为大众评委。
- 如果现场希望“只有导入用户可进入”，这里不符合。

建议：

- 改为无角色返回待授权页面。
- 或新增配置 `ALLOW_UNASSIGNED_FEISHU_PUBLIC=true`，默认 false。

### P2-7. 评委能否看未发布作品存在需求冲突

证据：

- 后端 bootstrap 对非 admin、非自己队伍用户只返回 published works：`server/siteStateService.js:102-112`。
- 前端详情权限里又允许 `permissions.canScore && Boolean(team?.work)` 看未发布作品：`src/site.js:249-259`。
- 测试也写了“privileged roles can open submitted work details”：`tests/logic.test.js:1140-1154`。

需求背景：

Jasper 后来明确说过“公共用户和评委只能看已发布”。因此当前后端过滤更接近新需求，但前端和测试还保留了“评委可看 submitted 作品详情”的旧口径。

建议：

- 如果最终需求是“评委只能看已发布”，则删除前端 `canScore` 未发布详情入口，并改测试。
- 如果评委需要评分未发布作品，则必须为评委提供单独的受控审核/评分列表，而不是从公众作品展厅偷入口。

### P2-8. 队伍进度查看权限与文档/产品预期可能不一致

证据：

- `judge` 和 `public` 的 `canViewTeamProgress` 都是 false：`src/logic.js:30-54`。
- 访问 team 视图会被重定向：`src/site.js:2542-2544`。

建议：

- 明确“队伍与成员页”是只给选手/管理员，还是评委/公众也可只读。
- 若只读开放，单独加 `canViewTeamProgressReadonly`，不要复用编辑权限。

## 6. P3：稳定性与工程质量问题

### P3-1. HTML/runtime-config 缓存头覆盖不完整

证据：

- Node 静态服务只写 `Content-Type`：`server/index.js:1583-1587`。
- Vercel 只对部分路径设置 no-store：`vercel.json:1-74`，未覆盖 `/site.html`、`/screen.html`、`/runtime-config.js`、`/styles.css`。

影响：

- 浏览器可能拿旧 HTML，导致脚本版本、样式、API Base 不更新。

建议：

- 所有 HTML 和 `runtime-config.js` 设置 `Cache-Control: no-store`。
- 带版本号的 JS/CSS 再考虑强缓存。

### P3-2. Docker 构建没有使用 lockfile，依赖版本不可复现

证据：

- Dockerfile 复制 `package*.json`：`Dockerfile:5`。
- `.dockerignore:5` 排除了 `package-lock.json`。
- Dockerfile 使用 `npm install --omit=dev`：`Dockerfile:7`。
- 依赖使用 `^` 范围：`package.json:10-13`。

影响：

- 同一份代码不同时间构建，可能安装到不同依赖版本。

建议：

- 不要忽略 `package-lock.json`。
- Dockerfile 改成 `npm ci --omit=dev`。

### P3-3. 部署脚本只部署远端 main，容易漏掉本地修复

证据：

- `deploy_to_88.sh:39-43` 固定 clone 远端 `main` 并构建。

影响：

- 本地刚修好的代码如果没 push 到 main，服务器不会更新。

建议：

- 部署脚本打印本地 commit、远端 commit、实际部署 commit。
- 支持 `DEPLOY_REF`。
- 部署前检查当前分支是否已 push。

### P3-4. 测试中有较多字符串断言，真实部署路径覆盖不足

证据：

- 现有测试大量用正则检查源码字符串，例如 `tests/logic.test.js` 多处读取 `admin.js/site.js` 后 `assert.match`。
- Docker/Vercel/缓存/Cookie 跨域没有真实集成测试。

影响：

- 代码文本存在不代表真实运行链路可用。

建议：

- 增加最小浏览器 smoke test：登录、后台打开、作品提交、管理员发布、作品展厅可见。
- 增加部署配置测试：Vercel 受限页不能裸访问，Docker 构建使用 lockfile。

## 7. 已经实现且应保留的保护

- 作品展厅只列出 published works：`src/site.js:2190-2220`。
- 后端可见作品过滤：admin 全量、player 自己队伍 + published、其他只 published：`server/siteStateService.js:102-112`。
- 正式作品提交会校验当前用户所属队伍：`server/index.js:1168-1169`。
- 投票接口会在投票窗口关闭时拒绝投票：`server/voteResultsRepository.js:67-70`、`server/mysqlVoteResultsRepository.js` 事务逻辑。
- JSON 投票仓库有串行写队列，避免同文件并发写互相覆盖：`server/voteResultsRepository.js:46-60`。
- 管理员端最终结果使用后端快照，而不是前端实时重新计算。
- 重置脚本已有 dry-run 和备份概念，适合继续扩展成正式运维工具。

## 8. 推荐修复路线

### 第 1 批：安全上线底线

1. 强制生产环境 strict + mysql，不满足直接启动失败。
2. 禁止 local-dev role login 默认开启。
3. 关闭 `/data/*` 静态暴露。
4. Vercel 或静态页部署增加页面级鉴权。

### 第 2 批：比赛流程闭环

1. 作品状态机：published 后不允许选手覆盖/撤销。
2. 上传作品图片时校验队伍归属。
3. 最终结果发布前检查评委评分完整/锁定。
4. 投票状态机禁止 published 回滚。
5. 最终快照发布做幂等。

### 第 3 批：部署和数据可靠性

1. 上传目录持久化或对象存储。
2. session 权限随角色变更失效。
3. MySQL 用户角色更新加事务。
4. 队伍成员增加数据库唯一约束。
5. Docker 使用 lockfile + `npm ci`。

### 第 4 批：测试补齐

1. 未登录不能访问管理 API。
2. 非管理员不能打开后台页面。
3. 选手不能上传其他队伍作品截图。
4. published 作品不能被选手撤销/覆盖。
5. 评委未锁定评分不能发布最终结果。
6. 重复发布最终结果不会生成多个快照。
7. 上传图片后重部署仍可访问。

## 9. 对 Jasper 的产品决策问题

下面几个不是纯代码问题，需要先定业务口径：

1. 评委是否只能看已发布作品？
   如果是，评分必须发生在作品发布之后；如果不是，需要给评委一个独立的“待评分作品”入口。

2. 最终发布是否允许缺少部分评委评分？
   如果允许，后台必须显示缺失清单并二次确认；如果不允许，后端应直接 409。

3. 已发布作品是否允许队伍在截止前更新？
   如果允许，需要“新版本待审 + 旧版本继续展示”；如果不允许，published 就应锁死。

4. 未授权飞书用户是否可以当大众评委？
   如果不可以，0 角色登录不能自动变 public。

## 10. 结论

当前项目已经进入“功能能跑，但流程边界还不够硬”的阶段。最需要修的不是 UI，而是：生产环境默认安全、作品审核状态机、最终结果发布条件、上传文件持久化、静态数据暴露。把这些修完后，这套系统才更接近真正可现场使用的比赛后台。
